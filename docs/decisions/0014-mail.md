# 0014 — Mail: a neutral Sender, one provider per vendor

Date: 2026-09-20
Status: accepted

## Context

Services send transactional mail through a vendor API in production, a
mail catcher in development, and nothing at all in tests. Code that builds
a message should not know which of the three is behind it. Two safety
needs come up in every service: a staging environment holding real data
must not mail real people, and webhooks posted by the vendor must be
verified before they change state.

## Decision

- `pkg/mail` in the root module is stdlib-only and provider-neutral:
  `Message` (with validation), the `Sender` interface, `SMTP` for mail
  catchers and relays, `Restrict` as the staging guard (every recipient,
  Bcc included, must be at an allowed domain), and `Recorder` for tests.
  Like `pkg/storage`, services import it directly.
- Vendors are providers on their official SDK. `providers/mailgun` offers
  `Sender(a)`, `VerifyWebhook` for delivery events and `ParseInbound` for
  routed messages, both checking Mailgun's HMAC signature and its
  freshness window through the SDK. `From(a)` is the SDK client.
- Templates are not part of mail. A service renders text and HTML with
  templ or `html/template` and hands strings to `Send`.
- There is no queue inside the sender. A service that must not block a
  request sends from a `gox/jobs` worker, which also gives retries.

## Consequences

- The SMTP sender builds a standard multipart message (alternative bodies,
  mixed when there are attachments, encoded headers) and authenticates with
  PLAIN only where net/smtp allows it: over TLS or to localhost.
- Another vendor is another provider implementing `mail.Sender`; nothing in
  a service changes but the option passed to `gox.New`.
